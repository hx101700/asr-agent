## 已确认的问题

### R01：上传持锁会阻塞目录取消（P2）

- 位置：`src/asr_agent/web.py:160`，`:189`，`:123`。
- `upload()`持有整个会话的RLock读取文件流；`cancel_directory()`必须先取得同一个锁，才能设置取消事件。页面允许目录窗口等待期间继续添加音频，因此正常操作可以触发这一组合。
- 已复现：模拟目录等待，然后让上传停在read；确认取消任务已开始后等待200毫秒，取消未完成、取消事件未置位。释放上传read后，取消才完成。无GUI、无网络、使用工作区临时合成数据。
- 影响：大文件、慢上传或等待数据时，“取消等待”响应被拖延。会话状态查询及退出清理也共享此锁，锁的范围过大。
- 最小方向：先将选择器取消控制与上传I/O锁分离；进一步让锁只保护必要状态变更，保留文件接收、校验与替换的完整性。无需引入队列或并发框架。

### R02：明确拒绝后的错误聚焦顺序不正确（P3）

- 位置：`src/asr_agent/static/app.js:575`及`:117`。
- 保存期间fieldset禁用；捕获字段级4xx时先showError/focus，之后才解除禁用。浏览器不会把焦点移入禁用控件。目录按钮还受updateButtons单独控制，不能只移动一行fieldset赋值就视为修复完成。

- 最小方向：先完成错误状态转换、恢复对应控件，再统一显示并聚焦错误；保存结果未知继续冻结。

## 待实际浏览器复核的问题

人数输入框使用type=number，表单禁用原生提交校验；`app.js:350`把空value当自动判断，未检查validity.badInput。合成DOM中`value=""`且`badInput=true`仍会提交null。浏览器数字输入可能处于这种状态，依据[WHATWG Number state](https://html.spec.whatwg.org/multipage/input.html#number-state-(type=number))；本轮未在Codex浏览器键入不完整数字实证，不能将特定键入场景写成已重现。

建议在序列化前检查badInput，并以一个窄范围真实浏览器测试验证。不要把Node中的最小DOM桩扩写为自制浏览器。

## 工程原则评价

| 原则 | 当前判断 | 应保留或调整的内容 |
| --- | --- | --- |
| KISS / YAGNI | 整体较好，局部有遗留 | 保留现有技术栈；清理死分支，不增加策略/工厂/事件总线 |
| 单一职责与内聚 | 部分符合 | auth/media等职责清楚；Session的状态控制与阻塞I/O需收敛 |
| DRY | 不够统一 | 前端多处写禁用/显示状态；多文档重复需求导致漂移 |
| 状态与副作用明确 | 需要改善 | 区分输入、临时操作状态、已校验快照；集中更新控件可用性 |
| 边界与可恢复性 | 有基础，仍有缺口 | 保留独占创建、文件指纹、取消/超时、不自动重试；补锁竞争场景 |
| 验证代表性 | 单测较充分，不能替代交互验收 | DOM桩无真实validity/禁用继承/焦点行为；实际GUI仍需实测 |

建议统一为“轻量分层+按用例编排”。前端可用一个普通状态对象和集中控件渲染函数，事件函数负责收集输入、验证、调用、更新状态；不要求引入状态机库。Python只提取具体职责明确的小函数/模块，不按每个原子操作建立接口和类层级。

## 固定整改设计（原提案，已按下列边界实施）

用户进一步要求轻量、固定、可扩展、易定位问题。目标明确为：**前端MVP（被动视图），后端应用服务层，外部能力采用薄适配器边界**。以下保留整改时的目标约定；995703e未采用，当前已实施情况见上表和DEVELOPMENT。

### 角色和依赖方向

| 角色 | 职责 | 边界 |
| --- | --- | --- |
| 前端Model | 流程阶段、正在进行的操作、预览版本、错误与回执；显式状态转换和无副作用的可用性判断 | 不访问DOM，不发送HTTP，不保存Key |
| 前端View | 读取表单原始输入及浏览器有效性；渲染控件、预览和错误；滚动/聚焦 | 不决定能否保存，不发请求，不直接修改Model |
| 前端Presenter | 接收用户事件，调用API/Model/View，处理异步结果和错误顺序 | 业务分支不读取DOM.disabled；不重写服务端验证 |
| HTTP Controller | 请求解析、来源/会话检查、调用用例、响应/错误映射 | 不实现Excel、媒体、目录进程或保存业务 |
| Application Service | Session中的上传、预览、确认和目录授权等用例；组织已有能力 | 不依赖HTTP状态码、浏览器元素或UI文案 |
| 本地能力/Adapter | 文件读写、PyAV、.env、原生窗口、已核实BL命令 | 不决定页面状态；BL已有功能继续直接复用 |

代码依赖固定为Presenter→Model/View/API入口，web→session→规则/本地能力。通过显式回调连接View事件与Presenter，不建立通用事件总线。新增有行为的类限于真实的状态/资源所有者（Session、目录选择控制对象）；保留Project、AudioInfo等已有且有意义的数据结构。普通规则和转换使用函数，不建立基类、工厂或每状态一个类。

### 前端状态约定

主流程phase采用有限值：loading、editing、validating、reviewing、saving、saved、save_unknown、unavailable。上传、读取Key、目录选择是可重叠的临时操作，分别记录其等待状态/请求标识，不合并成一个busy，也不为组合情况新增阶段。

- 普通表单输入由View读取，避免逐字同步到第二份JS表单副本。Model只存流程必需的状态和已接收的文件引用/预览；Key仅留在专用只读控件，不进入状态快照。
- Model导出canEdit/canValidate/canSave等派生结果；只有View渲染函数写控件的disabled/hidden，事件处理器不再散落设置这些属性。
- 校验期间编辑输入时增加revision、使预览失效，仍保留正在校验的状态；响应版本不符即丢弃，结束后回editing，不自动重发。
- 目录操作、Key读取按各自请求ID处理过期结果。目录取消保留原位置；目录选定后才使旧预览失效。
- 保存成功进入saved；明确可修正的拒绝回editing并丢弃旧预览；网络中断、无法判断是否已保存等进入save_unknown，禁止再次提交。任何finally都不能无条件把流程改回editing。
- 错误处理顺序固定为：更新Model → 渲染可用状态 → 展示错误 → 聚焦。初始化/会话不可用时显示对应错误，保留禁用状态。

### R01：并发修正

目录请求ID、取消事件和原生进程生命周期归目录选择控制对象，用独立的短控制锁维护；取消路径不经过Session的上传/校验锁。Session仅接收已完成的选择结果并登记输出授权，不在调用目录控制对象时持有会话锁。两个锁不嵌套等待。

上传按以下三个阶段处理：

1. 短锁检查会话仍开放，登记该类型正在上传及唯一标识，废弃旧预览。
2. 锁外接收文件到本次唯一.part文件；不提前把半成品登记为可校验的upload_id。
3. 短锁检查登记仍匹配且未进入保存/关闭，再发布完整文件引用。失败只清理本次文件；替换策略保持明确，不恢复已经失效的旧预览。

同一类型同时发来第二次上传时明确拒绝，不增加“多个上传竞速、最后一个胜出”的机制。校验/确认拒绝尚未完成的上传。退出清理先标记会话关闭，迟到的上传只能清理自身文件，不能重新发布结果。关闭后的清理与活动文件归属必须有测试。

此次只针对上传与目录取消的已知问题缩小锁范围。validate/confirm的幂等保存和指纹复核暂不顺带改为通用无锁事务；若后续需要释放这些I/O期间的锁，必须先处理快照版本和输入文件生命周期。
