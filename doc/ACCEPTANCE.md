## 恢复行为的证据

`tests/test_pip_download_contract.py` 使用包含合法 METADATA、WHEEL、RECORD 和 512 KiB 合成载荷的 wheel。服务仅监听 `127.0.0.1`，不安装这个测试包。

- 首个响应声明完整 Content-Length，却提前结束。pip 随后实际发出 Range 请求，收到 206 后完成下载；最终文件与合成原件逐字节、摘要均一致。
- 服务端忽略 Range、返回 200 时，pip 重新下载完整文件，结果同样一致。
- 完整文件的期望摘要故意设为不匹配值时，pip 返回失败，目标目录没有已保存的 wheel；没有修改摘要来使测试通过。

安装器测试另外验证：两个来源都失败后停止；首选源失败后仅切换一次；从本机 wheel 安装失败时不重新下载；已完整安装的环境跳过安装步骤。来源比较测试使用本机快慢响应，验证按文件吞吐排序、失败来源排后，以及服务器忽略 Range 时仍仅消费少量前缀。

`run_installer` 的实际小子进程测试证明首行日志在进程结束前已经输出并刷新，stdout 保留给最终回执；输入参数保真，用户中断或日志失败时子进程被回收。

## 复测

先准备独立合约环境：在项目内创建空的 `.runtime/skill-contract-workspace`，用当前 Skill 的 `scripts/asr.py`、该目录作为 `--workspace` 执行 bootstrap。BL 与 pip 合约共用这一环境，缺失或 pip 版本不符时相关测试明确跳过，不能计为通过。

本轮实际新目录为 `.runtime/download-acceptance`；测试驱动将 `tests.support.CONTRACT_WORKSPACE`、BL 入口及 SKILL_ROOT 指向该环境和新的 ZIP 解压位置，再确认所有 `asr_runtime` 模块从解压目录加载后运行发现测试。

常规开发检查：

```powershell
.venv\Scripts\python.exe -B -X utf8 -m unittest discover -s tests -t . -v
.venv\Scripts\python.exe -B -X utf8 -m mypy --config-file mypy.ini
```

修改前端时再执行 `npm run build:web`、`npm run test:web` 和 `npm run test:browser`。独立 ZIP 验收开始前确认专用目录没有用户数据和运行进程，清理后重新解压；普通用户的工作目录保留其任务和凭据。

## 验证边界

本轮依赖下载访问公开软件源，pip/BL 功能合约使用合成数据与本机服务，没有执行真实云端识别。测速只反映少量文件前缀的当时吞吐，不保证后续全程速度；原生续传也不跨镜像或进程保存未完成片段。

目标用户环境仍需验证新 Codex 对话的完整使用、真实账号与云端识别、原生目录窗口、接近限制的大录音和 Office 逐页视觉效果。云端转写失败不自动重试的约束保持不变。
